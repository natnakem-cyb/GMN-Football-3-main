# Contributing to GMN-Football-3

Thank you for contributing! This document covers everything needed to get a development environment running and submit changes that pass CI.

## Development Environment

GMN-Football-3 has two toolchains: TypeScript (game engine + browser app + Node bridge) and Python (RL training).

### Node / TypeScript

- Node.js 18+ (CI uses Node 24)
- ``npm install``

Common commands:

````
npm run dev              # Vite dev server (browser app) at http://localhost:3000
npm run build            # contract sync + tsc + vite build
npm run lint             # tsc --noEmit + contract sync check
npm run bridge           # headless training bridge (training/bridge_server.ts)
npm test                 # scenario + determinism test suites
````

### Python / RL Training

- Python 3.10+
- Install **only from ``training/requirements.txt``** - it is the single source of truth for Python dependencies (a former duplicate root ``requirements.txt`` has been removed):

````
pip install -r training/requirements.txt
````

**Adding a new Python dependency:** add it to ``training/requirements.txt`` only. Pin version bounds consistent with the existing entries (e.g. ``package>=x.y,<=x.z``) and note the version you verified against. Do not create additional requirements files.

### Training details

All training scripts, environment wrappers (Gymnasium ``training/gmn_gym.py``, PettingZoo ``training/gmn_pettingzoo.py``), parallel/vectorized stepping, self-play opponent pools, and full-match training are documented in [``training/README.md``](training/README.md).

## Coding Standards

### TypeScript

- ``tsconfig.json`` enforces ``strict`` mode **including** ``noUnusedLocals``, ``noUnusedParameters``, ``noImplicitReturns``, and ``noFallthroughCasesInSwitch``. ``npx tsc --noEmit`` must pass with zero errors.
- Prefix intentionally-unused parameters with ``_`` (e.g. ``_unused``); remove dead locals rather than suppressing them.
- The engine in ``src/engine/`` is authoritative for both the browser and training - never fork simulation logic.

### Python

- Follow PEP 8. Training scripts use argparse CLI conventions consistent with the existing ``training/train_*.py`` scripts.
- New environment/wrapper code must preserve the bridge contract (see below).

## Environment Contract (critical)

All contract constants (observation dim, action space, schema versions, event codes) are **single-sourced** in ``src/engine/Contract.ts`` and auto-generated into the Python wrappers by ``scripts/sync_contracts.ts``.

- Never hand-edit the ``# --- AUTOGENERATED CONTRACT CONSTANTS ---`` blocks in ``training/*.py``.
- If you change the contract shape, run ``npm run sync-contracts``, increment ``GMN_ENV_VERSION`` (minor bump), and update the ONNX/checkpoint tooling accordingly.
- CI runs ``npm run check:contracts`` and **fails on any drift**. ``npm run lint`` includes the same check locally.

## Testing Expectations

Before opening a PR, run:

- ``npm test`` - scenario validation + determinism suites (must be 100% deterministic).
- ``npm run lint`` - strict TypeScript + contract sync check.
- ``npm run test:pytest`` - full Python pytest suite (must pass).
- ``python3 training/tests/test_binary_frame_parser.py`` - targeted binary frame parser regression tests.
- Python tests relevant to your change, e.g. ``pytest training/tests`` or targeted scripts such as ``npm run test:gym-safety``, ``npm run test:pettingzoo``, ``npm run test:parity``.

Changes to the bridge protocol, reward computation, or environment wrappers must keep the existing transport-parity, reward-equivalence, and determinism tests passing.

## Pull Request Process

1. Fork / branch from ``main``.
2. Make your change and add/adjust tests.
3. Run the full test expectations above (and ``pytest`` for Python-side changes).
4. Ensure ``npm run check:contracts`` passes and documentation (this file, ``README.md``, ``training/README.md``) is updated for any new capability or script.
5. Update ``TASKS.md`` if your change completes or affects a tracked remediation item.
6. Open a PR describing *what changed and why*, including verification results (commands run + outcomes).

All submissions go through code review via GitHub pull requests before merging.
